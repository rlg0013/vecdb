# ADR 001: Float32 and Flat Vector Storage

**Status:** Accepted

**Date:** 2026-11-22

## Context

Our VectorDB requires an internal representation for high-dimensional numerical vectors.

We need a representation that supports:

- Efficient vector similarity calculations.
- Reasonable memory consumption.
- Contiguous memory access.
- Binary serialization and disk persistence.
- Efficient integration with Go's standard library.
- Future indexing algorithms such as HNSW.

We considered float32 versus float64 and nested versus flat vector storage.

## Decision 1: Use float32

We will use `float32` as the default vector element type.

### Reasons

1. **Memory efficiency:** A float32 occupies 4 bytes, compared with 8 bytes for float64.
2. **Dataset compatibility:** Our SIFT1M dataset uses float32 values.
3. **Cache efficiency:** Smaller representations allow more vector values to fit into CPU caches.
4. **Storage efficiency:** Binary persistence requires less disk space.
5. **Common industry practice:** Float32 is a widely used representation for embedding and similarity-search workloads.

### Trade-offs

Float32 provides less numerical precision than float64.

This is acceptable for our initial similarity-search implementation, but numerical accuracy will be validated through testing and benchmarking.

## Decision 2: Use flat []float32 storage

Our internal vector storage will use contiguous flat slices rather than independently allocated slices for every vector.

For a dataset with N vectors and D dimensions, the logical layout is:

`data[N * D]float32`

The vector at index i starts at:

`data[i * D : (i+1) * D]`

### Reasons

1. **Contiguous memory:** Vector values are stored sequentially.
2. **Cache locality:** Sequential access improves memory access patterns during distance calculations.
3. **Reduced allocation overhead:** We avoid maintaining one separately allocated slice for every vector.
4. **Simpler serialization:** The underlying values can be written sequentially to binary storage.
5. **Predictable indexing:** Vector offsets can be calculated directly using the vector ID and dimensionality.

### Trade-offs

- The dimensionality must be consistent within a storage collection.
- Growing the backing slice can require allocation and copying.
- Individual vector deletion requires additional bookkeeping or compaction.
- Concurrent access requires synchronization.

## Alternatives considered

### float64

Rejected as the default representation because it doubles memory consumption and is unnecessary for our initial embedding workloads.

It may still be useful for selected numerical calculations.

### [][]float32

Rejected as the primary large-scale storage representation because each vector has its own slice header and potentially separate backing allocation.

It remains useful as an input/output API representation and for dataset loading.

### Separate allocation per vector

Rejected because it increases allocation overhead and can reduce memory locality.

## Consequences

The project will use:

- `float32` for vector values.
- Flat `[]float32` storage for the main vector store.
- An explicit dimensionality field for each collection.
- Calculated offsets for accessing individual vectors.
- `[][]float32` where convenient for external APIs and dataset loading.

Future implementations must benchmark this choice against alternative layouts before changing the storage representation.
